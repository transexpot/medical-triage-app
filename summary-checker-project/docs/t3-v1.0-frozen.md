# ТЗ v1.0 — Прототип «Формальная проверка сводок»

**Статус:** FROZEN (BLOCKED)  
**Версия ТЗ:** v1.0  
**Дата freeze:** 2026-11-13  
**Статус пилота:** INTERNAL_TEST, NOT_INDEPENDENT  

Спецификация заморожена, но не может быть введена в действие до закрытия SPEC_DEFECT-003 и SPEC_DEFECT-004. Первый спринт не начинается, пока не закрыты SPEC_DEFECT-003, SPEC_DEFECT-004 и SPEC_DEFECT-005.

## 1. Назначение

Этот документ определяет поведение прототипа v1 «Формальная проверка сводок».

Система принимает синтетические или обезличенные сводки, выполняет формальные проверки данных, классифицирует дефекты и вычисляет статус сводки.

Система не принимает клинических решений.

## 2. Границы v1

### Входит в v1

- Приём 5 синтетических или обезличенных сводок в JSON.
- Выполнение 7 формальных проверок.
- Классификация дефектов.
- Вычисление статуса сводки.
- Вычисление булева флага `data_complete`.
- Карантин дефектных значений.
- Пересчёт `clinical_use_deadline`.
- Запись событий в append-only журнал с хеш-цепочкой.

### Не входит в v1

- E1: согласие, доступ, оспаривание, представительство пациента.
- E2: `VIEWED`, `ACKNOWLEDGED`, клиническое решение врача.
- Независимый аудит.
- Полноценный интерфейс врача.
- Обработка реальных персональных данных.
- Клиническая интерпретация значений.
- Оценка референсных диапазонов.
- Оценка динамики показателей.

## 3. Роли

| Роль | Может | Не может |
|---|---|---|
| Исполнитель | Создать черновик сводки | Запускать проверку, классифицировать дефект, менять статус |
| Проверяющий T1 | Запустить проверку, выбрать `passed`, `failed` или `cannot_verify` | Менять статус вручную, менять критичность |
| Система | Вычислять статус, флаг, карантин, SLA | Принимать решения вне правил |
| Внутренний контролёр | Читать журнал, запускать `verify_chain` | Менять журнал или конфигурацию |
| Внешний рецензент | Читать отчёты, выдавать заключение, блокировать переход к реальным данным | Редактировать журнал, участвовать в разработке |

## 4. Модель данных

### 4.1. Поля сводки

| Поле | Тип | Обязательное | При отсутствии | При дефекте |
|---|---|---|---|---|
| `patient_ref` | string | да | `BLOCKER` | `BLOCKER` |
| `summary_id` | UUID | да | `BLOCKER` | `BLOCKER` |
| `glucose_value` | decimal | да | `BLOCKER` | `BLOCKER` |
| `glucose_unit` | enum | да | `BLOCKER` | `BLOCKER` |
| `glucose_condition` | enum | да | `BLOCKER` | `BLOCKER` |
| `glucose_measurement_date` | ISO date | да | `BLOCKER` | `BLOCKER` |
| `glucose_source` | source reference | да | `BLOCKER` | `BLOCKER` |
| `hba1c_value` | decimal | нет | не дефект | `BLOCKER` |
| `hba1c_unit` | enum | нет | не дефект | `BLOCKER` |
| `hba1c_measurement_date` | ISO date | нет | не дефект | `BLOCKER` |
| `hba1c_source` | source reference | нет | не дефект | `BLOCKER` |
| `weight_value` | decimal | нет | не дефект | `WARNING` |
| `weight_unit` | enum | нет | не дефект | `WARNING` |
| `weight_measurement_date` | ISO date | нет | не дефект | `WARNING` |
| `weight_source` | source reference | нет | не дефект | `WARNING` |

### 4.2. Правило критичности

Отсутствие необязательного поля не является дефектом.

Но если необязательное критическое поле присутствует, оно обязано иметь дату, единицы и проверяемый источник.

Иначе это `BLOCKER`.

### 4.3. Карантин

Дефектное значение не удаляется.

Оно перемещается в `quarantined_values`, участвует в расчёте статуса и не передаётся врачу как валидное клиническое значение.

## 5. Формальные проверки

| `check_id` | Проверка | Допустимые ответы |
|---|---|---|
| `patient_identity` | Идентификатор пациента присутствует и совпадает во всех документах | `passed`, `failed`, `cannot_verify` |
| `value_date_present` | У каждого присутствующего значения есть дата | `passed`, `failed`, `cannot_verify` |
| `value_source_present` | У каждого присутствующего значения есть источник | `passed`, `failed`, `cannot_verify` |
| `unit_valid` | Единицы присутствуют и входят в допустимый enum | `passed`, `failed`, `cannot_verify` |
| `glucose_condition_valid` | Условие измерения глюкозы указано | `passed`, `failed`, `cannot_verify` |
| `value_readable` | Значение читаемо, не пустое, не содержит заглушек | `passed`, `failed`, `cannot_verify` |
| `contract_compliance` | Данные соответствуют контракту: типы, форматы, enum, отсутствие неизвестных полей | `passed`, `failed`, `cannot_verify` |

Запрещённые формулировки:

```text
значимо
нормально
подозрительно
достаточно
клинически корректно
```

## 6. Классы дефектов

| Класс | Значение |
|---|---|
| `BLOCKER` | Данные нельзя передавать врачу |
| `WARNING` | Данные можно передавать с видимым предупреждением |
| `NEEDS_CLARIFICATION` | Проверяющий не может однозначно завершить проверку |

## 7. Статусы и флаг

| Состояние | Статус | `data_complete` | Передача врачу |
|---|---|---|---|
| Нет дефектов | `READY_FOR_PHYSICIAN` | `true` | Да |
| Есть предупреждения | `READY_WITH_WARNINGS` | `true` | Да, с видимым предупреждением |
| Есть уточнение | `NEEDS_CLARIFICATION` | `false` | Нет |
| Есть блокер | `BLOCKED` | `false` | Нет |
| Данные полны, срок истёк | `DEADLINE_MISSED` | `true` | Нет |
| Приём отменён | `ARCHIVED` | не вычисляется | Нет |

Приоритет статусов:

```text
BLOCKED > DEADLINE_MISSED > NEEDS_CLARIFICATION
> READY_WITH_WARNINGS > READY_FOR_PHYSICIAN
```

`data_complete = true`, если:

- все обязательные поля присутствуют;
- все присутствующие критические поля имеют дату, единицы и источник;
- нет блокеров;
- нет открытых уточнений;
- нет значений в карантине по критическим полям.

Предупреждения не делают `data_complete = false`.

## 8. Журнал

Журнал является append-only.

Запрещены `UPDATE` и `DELETE`.

Формула хеша:

```text
event_hash = SHA-256(canonical_event || previous_hash)
```

Обязательные поля события:

```text
event_id
summary_id
event_type
sequence
occurred_at
actor_id
actor_role
schema_version
payload
previous_event_hash
event_hash
```

`sequence` — монотонный номер внутри `summary_id`.

`event_id` — уникальный идентификатор события.

`occurred_at` — ISO-8601 UTC.

## 10. Перенос приёма

Проверки сохраняются, если не изменились:

- данные;
- источник;
- версия чек-листа;
- версия карты критичности;
- версия карты оснований.

При переносе приёма без изменения основания:

```text
APPOINTMENT_RESCHEDULED
→ CHECKS_PRESERVED
→ DEADLINE_RECALCULATED
→ STATUS_COMPUTED
→ FLAG_COMPUTED
```

При переносе запрещены новые:

```text
CHECK_PASSED
CHECK_FAILED
VALUE_QUARANTINED
DEFECT_CLASSIFIED
```

Если ранее был `DEADLINE_MISSED`, а новый дедлайн в будущем, создаётся:

```text
DEADLINE_MISSED_CLEARED
```

## 11. Отмена и повторное назначение

При отмене приёма:

```text
APPOINTMENT_CANCELLED
→ CHECKS_PRESERVED
→ DEADLINE_CANCELLED
→ STATUS_COMPUTED
→ FLAG_COMPUTED
```

Ожидаемый статус:

```text
ARCHIVED
```

При повторном назначении приёма:

```text
APPOINTMENT_RESCHEDULED
→ CHECKS_PRESERVED
→ DEADLINE_RECALCULATED
→ STATUS_COMPUTED
→ FLAG_COMPUTED
```

Сводка деархивируется, а история отмены и архивации сохраняется.

## 12. Карта оснований

Каждая проверка имеет основание:

```text
поля проверки
+ fingerprint источника
+ checklist_version
+ criticality_map_version
+ check_basis_map_version
```

Изменение карты оснований требует двойного утверждения:

1. Владелец чек-листа.
2. Внешний рецензент.

После изменения:

```text
CHECK_BASIS_MAP_VERSION_CHANGED
→ ALL_CHECKS_INVALIDATED
```

В v1 действует ограничение:

```text
SINGLE_EXTERNAL_REVIEWER
```

Один внешний рецензент утверждает обе критические конфигурации:

- `CRITICALITY_MAP_CHANGED`
- `CHECK_BASIS_MAP_VERSION_CHANGED`

Ограничение снимается в v1.5.

## 13. Feature flags

В v1 разрешён только один флаг:

```text
enable_weight_source_check
```

Он может отключать только некритичную проверку источника веса.

Любое изменение флага создаёт:

```text
FEATURE_FLAG_CHANGED
```

Отключение критической проверки запрещено.

## 14. Метрики v1

| Метрика | Формула |
|---|---|
| FPR | Ложные дефекты / все отмеченные дефекты |
| FNR | Пропущенные дефекты / все реальные дефекты |
| Время обработки | Медиана от получения до статуса |
| Доля `cannot_verify` | Запросы на уточнение / все проверки |

FNR в v1 считается против синтетического эталона.

## 15. Acceptance-кейсы

Всего 14 acceptance-кейсов.

| ID | Тест | Ожидаемый результат |
|---|---|---|
| `AT-001` | Все обязательные поля корректны | `READY_FOR_PHYSICIAN`, `data_complete = true` |
| `AT-002` | Нет даты глюкозы | `BLOCKED`, `data_complete = false` |
| `AT-003` | Неверный формат даты веса | `READY_WITH_WARNINGS`, `data_complete = true` |
| `AT-004` | Источник вне справочника | `NEEDS_CLARIFICATION`, `data_complete = false` |
| `AT-005A` | Перенос на будущую дату | `CHECKS_PRESERVED`, нет новых `CHECK_*` |
| `AT-005B_COMPLETE` | Перенос на прошлое, данные полны | `DEADLINE_MISSED`, `data_complete = true` |
| `AT-005B_BLOCKER` | Перенос на прошлое, есть блокер | `BLOCKED`, `data_complete = false`, `DEADLINE_MISSED` |
| `AT-005C` | Двойной перенос | Активен последний дедлайн |
| `AT-005D` | Отмена приёма | `ARCHIVED` |
| `AT-005E` | Отмена и новое назначение | Деархивация, новый дедлайн |
| `AT-006` | Целостность журнала | `verify_chain()` проходит |
| `AT-007` | Разделение полномочий | Запрещённые действия отклонены |
| `AT-008` | Метрики против ground truth | FPR и FNR совпадают с эталоном |
| `AT-009` | Детерминизм | Одинаковый вход — одинаковый результат |

## 16. Exit-критерий спринта

Спринт считается завершённым, если одновременно выполнены все условия:

1. `AT-001`–`AT-004` дают ожидаемый результат.
2. `AT-005A`, `AT-005B_COMPLETE`, `AT-005B_BLOCKER`, `AT-005C`, `AT-005D` и `AT-005E` дают ожидаемый результат.
3. `verify_chain()` проходит до и после тестов.
4. `UPDATE` и `DELETE` журнала отклонены.
5. Подмена записи разрывает цепочку.
6. Проверяющий не может вручную изменить статус.
7. Исполнитель не может запускать проверку.
8. Отключение критической проверки запрещено.
9. FPR и FNR совпадают с синтетическим эталоном.
10. Повторный запуск движка даёт идентичный результат.
11. `SPEC_DEFECT` останавливает затронутый тест.
12. Последовательности событий соответствуют спецификации.
