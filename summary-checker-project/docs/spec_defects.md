## SPEC_DEFECT-003

```text
ID: SPEC_DEFECT-003
Статус: OPEN
Приоритет: P1
Блокирует первый спринт: да
Блокирует тест: AT-005B_COMPLETE
Влияет на: раздел 7 и AT-005B_COMPLETE

Описание:
В ТЗ v1.0 есть прямое противоречие.

В таблице статусов указано:

DEADLINE_MISSED → data_complete = true

Но в определении data_complete указано:

data_complete = true, если активный приём существует
и его дедлайн не истёк.

DEADLINE_MISSED означает, что дедлайн истёк.
Следовательно, формула и таблица противоречат друг другу.

AT-005B_COMPLETE не может быть зелёным
при текущей формулировке.

Решение:
Принят вариант (а).

data_complete — свойство данных,
а не свойство времени.

Убрать из определения data_complete условие:
«активный приём существует и его дедлайн не истёк».

Оставить:
data_complete = true,
если все обязательные поля присутствуют,
все присутствующие критические поля имеют дату,
единицы и источник,
нет блокеров и нет открытых уточнений.

DEADLINE_MISSED остаётся отдельным статусом
и отдельным признаком времени.

Исправленный фрагмент ТЗ:

data_complete = true,
если:
- все обязательные поля присутствуют;
- все присутствующие критические поля имеют дату,
  единицы и источник;
- нет блокеров;
- нет открытых уточнений;
- нет значений в карантине по критическим полям.

Условие «дедлайн не истёк» исключается.

Шаги воспроизведения:
1. Открыть docs/t3-v1.0-frozen.md.
2. Перейти в раздел 7 «Статусы и флаг».
3. В таблице статусов найти строку DEADLINE_MISSED.
4. Зафиксировать значение data_complete = true.
5. В том же разделе найти определение data_complete.
6. Найти условие:
   «активный приём существует и его дедлайн не истёк».
7. Сопоставить таблицу и определение.
8. Зафиксировать противоречие.

Ожидаемый результат:
Таблица статусов и определение data_complete
не противоречат друг другу.

Фактический результат:
Таблица утверждает:
DEADLINE_MISSED → data_complete = true.

Определение утверждает:
data_complete = true только при неистёкшем дедлайне.

DEADLINE_MISSED означает, что дедлайн истёк.
Следовательно, оба фрагмента противоречат друг другу.

Затронутый критерий приёмки:
AT-005B_COMPLETE.

Порядок закрытия:

SPEC_DEFECT-003 является изменением контракта.

Изменение затрагивает:
- определение data_complete;
- семантику статуса DEADLINE_MISSED;
- acceptance-кейс AT-005B_COMPLETE.

Закрытие SPEC_DEFECT-003 требует двойного утверждения:

1. Владелец чек-листа.
2. Внешний рецензент.

После двойного утверждения:
- создаётся ТЗ v1.1;
- исправляется определение data_complete;
- создаётся событие CHECKLIST_VERSION_CHANGED;
- обновляется changelog;
- SPEC_DEFECT-003 переводится в RESOLVED.

Запрещено закрывать SPEC_DEFECT-003
односторонним решением оператора.

Ограничение:
Freeze v1.0 остаётся недействительным,
пока SPEC_DEFECT-003 открыт.

После исправления создаётся ТЗ v1.1.
```

## SPEC_DEFECT-004

```text
ID: SPEC_DEFECT-004
Статус: OPEN
Приоритет: P1
Блокирует первый спринт: да
Блокирует тест: AT-005A, AT-005B_COMPLETE, AT-005B_BLOCKER
Влияет на: CHECKS_PRESERVED и раздел 12

Описание:
В ТЗ v1.0 определена карта оснований проверок
и событие CHECKS_PRESERVED.

Но файла check_basis_map.json нет
ни в src/,
ни в docs/,
ни в tests/.

Без карты оснований невозможно вычислить:
- какие проверки сохраняются при переносе;
- какие проверки перезапускаются;
- какие поля входят в data_fingerprint;
- какие источники входят в source_fingerprint.

Следовательно, CHECKS_PRESERVED невычислим,
а AT-005A не может быть зелёным.

Решение:
Создать файл:

src/summary_checker/check_basis_map.json

с версией:

check_basis_map_version = v1.0

Файл должен содержать карту:

check_id → fields + source + versions

для всех семи проверок v1:
- patient_identity;
- value_date_present;
- value_source_present;
- unit_valid;
- glucose_condition_valid;
- value_readable;
- contract_compliance.

Шаги воспроизведения:
1. Открыть docs/t3-v1.0-frozen.md.
2. Перейти в раздел 12 «Карта оснований».
3. Найти упоминание check_basis_map_version.
4. Найти упоминание CHECKS_PRESERVED.
5. Открыть каталог src/.
6. Открыть каталог docs/.
7. Открыть каталог tests/.
8. Выполнить рекурсивный поиск файла
   check_basis_map.json
   в каталогах src/, docs/ и tests/.
9. Зафиксировать результат поиска.

Ожидаемый результат:
Файл check_basis_map.json существует
и содержит карту оснований для всех семи проверок v1.

Фактический результат:
Файл check_basis_map.json отсутствует.
Рекурсивный поиск также не находит файл
в подкаталогах src/, docs/ и tests/.

Следовательно:
- невозможно определить поля каждой проверки;
- невозможно определить источник каждой проверки;
- невозможно определить версии, от которых зависит проверка;
- невозможно вычислить CHECKS_PRESERVED;
- AT-005A не может быть зелёным.

Затронутый критерий приёмки:
AT-005A, AT-005B_COMPLETE, AT-005B_BLOCKER.

Порядок закрытия:

SPEC_DEFECT-004 закрывается через ТЗ v1.1.

Основание:
В разделе 12 ТЗ v1.0 указано только,
что каждая проверка имеет основание
и что существует check_basis_map_version.

Но полная карта оснований не была специфицирована:
не определены поля, источники и версии
для каждой из семи проверок.

Следовательно, создание check_basis_map.json
является дополнением контракта,
а не восстановлением пропущенного файла.

После создания карты:
- создаётся ТЗ v1.1;
- карта проходит двойное утверждение:
  владелец чек-листа и внешний рецензент;
- создаётся событие CHECK_BASIS_MAP_VERSION_CHANGED;
- обновляется changelog;
- SPEC_DEFECT-004 переводится в RESOLVED.

Запрещено закрывать SPEC_DEFECT-004
как простой repo fix,
пока карта не специфицирована и не утверждена.

Ограничение:
Freeze v1.0 остаётся недействительным,
пока SPEC_DEFECT-004 открыт.

После создания карты создаётся ТЗ v1.1
или подтверждается, что карта была частью v1.0,
но не была включена в репозиторий.
```

## SPEC_DEFECT-005

```text
ID: SPEC_DEFECT-005
Статус: OPEN
Приоритет: P2
Ответственный: владелец чек-листа
Блокирует первый спринт: да
Блокирует тест: AT-001–AT-009
Влияет на: exit-критерий раздела 16

Описание:
В ТЗ v1.0 определены 14 acceptance-кейсов:
AT-001, AT-002, AT-003, AT-004,
AT-005A, AT-005B_COMPLETE, AT-005B_BLOCKER,
AT-005C, AT-005D, AT-005E,
AT-006, AT-007, AT-008, AT-009.

Но в tests/integration/ нет явной связи
между файлами тестов и ID acceptance-кейсов.

Существующие файлы:
- test_invalid_summary_flow.py
- test_physician_review_flow.py
- test_quarantine_flow.py
- test_summary.py

Ни один файл не назван по ID acceptance-кейса.
Нельзя доказать, что каждый из 14 кейсов
проверяется хотя бы одним тестом.

Следовательно, exit-критерий раздела 16
не может быть проверен объективно.

Решение:
До начала первого спринта создать файл:

tests/README.md

и добавить таблицу трассируемости.

Таблица ниже — пример формата,
а не утверждение о фактическом покрытии.

Фактическое покрытие определяется только
после анализа реальных тестов в tests/integration/.

| Acceptance-кейс | Тестовый файл | Тестовый кейс | Статус покрытия | Примечание |
|---|---|---|---|---|

| AT-002 | TBD | TBD | UNCOVERED | Требуется анализ |
| AT-003 | TBD | TBD | UNCOVERED | Требуется анализ |
| AT-004 | TBD | TBD | UNCOVERED | Требуется анализ |
| AT-005A | TBD | TBD | UNCOVERED | Требуется анализ |
| AT-005B_COMPLETE | TBD | TBD | UNCOVERED | Требуется анализ |
| AT-005B_BLOCKER | TBD | TBD | UNCOVERED | Требуется анализ |
| AT-005C | TBD | TBD | UNCOVERED | Требуется анализ |

Запрещено заполнять таблицу

Каждая строка должна быть подтверждена
реальным тестом или явно помечена как UNCOVERED.

Ответственный за заполнение таблицы:
владелец чек-листа.

Ответственный за подтверждение покрытия:
внешний рецензент.

Таблица заполняется только после:
1. Закрытия SPEC_DEFECT-003.
2. Закрытия SPEC_DEFECT-004.
3. Создания ТЗ v1.1.
4. Написания реальных тестов.
5. Запуска реальных тестов.

Запрещено закрывать SPEC_DEFECT-005
по предположению о покрытии.

Шаги воспроизведения:
1. Открыть раздел 15 ТЗ v1.0.
2. Перечислить все 14 acceptance-кейсов.
3. Открыть tests/integration/.
4. Попытаться сопоставить каждый AT-ID
   с конкретным тестовым файлом.
5. Проверить, что каждый AT-ID покрыт.

Ожидаемый результат:
Каждый из 14 acceptance-кейсов
имеет явную связь хотя бы с одним тестовым файлом.

Фактический результат:
Связь отсутствует.
Нельзя установить, какой файл проверяет какой AT-ID.

Затронутый критерий приёмки:
Раздел 16, exit-критерий спринта:
все 14 acceptance-кейсов должны быть зелёными.
```
